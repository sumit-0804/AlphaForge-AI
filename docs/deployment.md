# Deployment and CI

Cloud Run via Cloud Build, the GitHub Actions pipeline, and regenerating the diagrams.

## Deployment

Both services run on **Cloud Run**, built and deployed by a **Cloud Build trigger**
connected to GitHub and pointed at `cloudbuild.yaml`. Everything is set up in the
Cloud Console; `gcloud` runs only on Google's build workers.

What the pipeline does:

1. Builds and pushes `backend` to Artifact Registry
   (`asia-south1-docker.pkg.dev/$PROJECT_ID/alphaforge`).
2. Deploys `alphaforge-backend`: 1 CPU / 1 GiB, scale to zero, 900 s request timeout
   (for SSE), runtime service account `alphaforge-run`. Plain env vars are set in the
   file; `MONGODB_URI`, `GOOGLE_API_KEY` and `JWT_SECRET` come from Secret Manager
   (`alphaforge-mongodb-uri`, `alphaforge-google-api-key`, `alphaforge-jwt-secret`).
3. Reads the backend URL and builds `frontend` with it as the `NEXT_PUBLIC_API_URL`
   build arg.
4. Deploys `alphaforge-frontend`: 1 CPU / 512 MiB, scale to zero.
5. Points the backend's `CORS_ORIGIN` at the frontend's URL.

One-time setup in the Console:

- Enable the Cloud Run, Artifact Registry, Cloud Build and Secret Manager APIs, and
  create the `alphaforge` Docker repository in `asia-south1`.
- Create the three secrets.
- Create two service accounts: a build account with *Cloud Run Admin*, *Artifact
  Registry Writer*, *Service Account User* and *Logs Writer*, and `alphaforge-run`
  with only *Secret Manager Secret Accessor*.
- Create the trigger with the build account, pointed at `cloudbuild.yaml`.
- In Atlas, create the vector index and allow Cloud Run's egress in the network
  access list.

Why this shape:

- **The backend is stateless.** Memory vectors live in Atlas, checkpoints and quota
  counts in Mongo — nothing is on local disk, so instances can scale to zero.
- **No detached background work.** Cloud Run throttles CPU after the response, so
  anything that must happen (like reflection after a sell) is awaited in request
  scope.
- **The frontend can't use Cloud Run's "deploy from repository" autodetect**, because
  `NEXT_PUBLIC_API_URL` has to be a Docker build arg.

## CI

`.github/workflows/ci.yml` runs on pushes and pull requests to `main`:

| Job | Steps |
| --- | --- |
| `frontend` | `npm ci`, `tsc --noEmit`, `npm run lint`, `npm run build` |
| `backend` | `uv sync --frozen`, then imports the app and asserts the OpenAPI schema exposes at least 25 paths |
| `images` | Builds both Docker images with Buildx (no push) |

## Regenerating the diagrams

```powershell
cd backend
.\.venv\Scripts\python.exe ..\docs\generate_diagrams.py
```

| Diagram | Source | Drift risk |
| --- | --- | --- |
| `mermaid.png` | Exported from the compiled workflow graph | None — derived from code |
| `debate-subgraph.png` | Exported from the compiled debate graph | None — derived from code |
| `system.png` | Hand-authored `system.mmd` | **Can drift** — update when the architecture changes |
| `agent-*.png` | Hand-authored `agent-*.mmd` | **Can drift** — update when an agent's flow changes |

The two graph exports are generated by LangGraph from the compiled objects, so they
always match the code. The rest are maintained by hand, because no single graph object
spans the API surface, the standalone agents and the trade-close reflection path.

> PNGs are rendered via the mermaid.ink web service. Pass `--mmd-only` to refresh just
> the generated `.mmd` sources with no network call. The `.mmd` files are committed
> alongside the images so every diagram stays reviewable in plain text.
